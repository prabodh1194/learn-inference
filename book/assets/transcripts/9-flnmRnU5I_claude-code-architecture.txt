Where does the thinking actually happen?

If a tool use request is the model's

Many are switched on by feature flags or

The full instruction manual for a tool

reaches for it. The action surface is

Now the gate that every single action

Here is the resource that quietly
governs everything else, the context
window. Older models get 200,000 tokens,
the newest ones around a million, and it
is always, eventually, the binding
constraint. Every file read, every
command output, every prior turn
competes for that space, and when it
fills up, quality falls off a cliff. So,
Claude code manages it like a memory
manager, not a garbage bin. Five
compaction layers run in sequence before
every model call. Gentlist first. Budget
reduction trims individual tool outputs
that are too big. Snip drops the oldest
history segments. Micro compact does
fine-grained, cache-aware compression.
Context collapse replaces a stretch of
history with a summary, but as a
read-time projection, so the full record
still exists underneath. And only if all
of that still isn't enough does auto
compact fire. A full, model-written
summary of the whole conversation. It's
lazy degradation. Spend the cheapest,
least destructive move first, and
escalate only when you're actually
forced to.
Compaction handles the conversation
while it's in flight. But what about the
things you want the agent to remember
every single time? That's a separate
system, and its defining choice is
radical transparency. Instead of an

personal global file, down to a project

code you're working on load later, and
win more of the model's attention. And
they're lazy. Deep directory

they deliberately did not build. No

the agent was told.
Now, how do you let people extend this
thing without drowning it? Most
frameworks give you one mechanism.
Everything you add is a tool. Claude
code deliberately ships four, and the
reason is beautiful once you see it.
They're sorted by how much context they
cost. At the free end are hooks, little
bits of code that fire on lifecycle
events to block, rewrite, or annotate
actions. They cost zero context by
default. Skills cost a little. Only a
short description sits in the prompt,
and the full instructions load when the
skill is actually invoked. Plugins are
the packaging layer, bundling any of the
others together for distribution. And
MCP servers, which give the model brand
new callable tools, cost the most
because every tool's schema has to live
in the window. So, the four aren't
redundant. They span a range from zero
cost event handlers all the way to
expensive full integrations. A single
mechanism could never cover that spread
without forcing everyone to pay the
maximum price. And each one plugs into a
different moment of the loop, what the
model sees, what it can reach, and
whether an action runs.
Sometimes the smartest move is to not do
the work yourself. Say fixing one
failing test means first understanding
an entire authentication module, a big
messy exploration that would flood your
context with dead ends. So, the agent
spawns a subagent, and the key design
choice here is isolation. The subagent
gets its own fresh context window, its
own tool set, does the messy
exploration, and returns only a short
summary to the parent. All the noise,
the 20 files it read, the wrong turns,
stays in a separate transcript on disk
called a side chain and never touches
the parent's window. It's delegation as
context hygiene. You get the answer
without inheriting the mess. Sub agents
can even run inside a temporary Git work
tree, their own private copy of the
repo, so they can edit freely without
stepping on your main branch. It is not
free. Running whole teams of agents can
burn something like seven times the
tokens of a normal session, which is
exactly why that summary only return
matters so much.
It's worth a quick detour on planning,
because it's delightfully anticlimactic.
Claude code has a plan mode and a

described that tool as basically a
no-op. It doesn't compute anything. It
doesn't call the outside world. So, why
does it even exist? Because writing the
plan down keeps the agent on track. The

It's that laying out the steps focuses
the model's own reasoning, and it gives
you a clean checkpoint to approve before
anything actually runs. And this is the
whole philosophy in miniature. The
harness doesn't impose a rigid planning

scratch pad and gets out of the way.
Minimal scaffolding, maximal room for
the model to think.
A production tool spends a shocking
amount of its code on things going
wrong, and how it chooses to fail is
itself a design decision. The principle
here is recover silently and only spend
the human's precious attention on what's
genuinely unrecoverable. Hit the output
token cap in the middle of an answer?
Retry with a bigger limit, up to three
times. Context about to overflow?
Reactively compact just enough to make
room. The API rejects the prompt as too
long? Try collapsing history and
compacting before you give up. A
streaming hiccup or the model itself
failing? Fall back to a different
strategy or to a backup model entirely.
And Every one of these could have been a
hard error thrown in your face. Instead,
they're quietly caught and routed
around. It's the exact same pattern as a
denied permission. A failure becomes a
signal the system acts on, not a wall it
slams into. The whole agent is built to
bend rather than break.
Where does all of this lie between turns
and across restarts? On disk as
append-only logs. One file per session,

Append-only is a surprisingly strong

human-readable and auditable. You trade

like friction, and that's the point.
Each session is treated as its own

Now, the move that makes this an actual
study and not a fan letter. The authors
take the exact same design questions to
two other agent systems built from
completely different starting points. A
multi-channel assistant gateway and a
single process assistant serving many
surfaces, plus the wider world of coding
agents. And the answers genuinely
diverge. Take safety. Claude code puts
the trust boundary between the model and
your machine, checking every single
action, deny first. Container isolated
agents like SWE agent and open hands
make a totally different bet. Wrap the
whole thing in a sandbox and let it run
freely inside. Ada makes a third bet
entirely. Skip per-action checks and use
Git as the safety net, so every change
is reversible. Same question. How do I
stay safe in three completely different
architectures? The gateway system pushes
the boundary all the way out to the
perimeter, checking who's allowed in
rather than what each action does. The
lesson isn't that one of them is right.
It's that the questions are universal
and the deployment context is what
decides the answer.
Step back far enough and a familiar
shape emerges. A tiny reasoning core
wrapped in a thick shell of
deterministic services for permissions,
tools, memory, and recovery. If that
sounds like something, it should. It's
an operating system. The loop is the
kernel. Everything around it is the OS,
virtualizing the messy real world into
safe, structured calls the model is
allowed to make. And this reframes
what's actually being built here. As
frontier models converge, as they all
get roughly, dependably good at coding,
the model stops being the
differentiator. The harness becomes it.
The paper argues, and this is the part
one keep chewing on, that investing in
boring infrastructure, context

an already capable model. The

Is that just a nice story, or is it
actually measurable? It's measurable.

Now, the honest part, because this paper
is refreshingly willing to point at its
own subject's cracks. Layering safety
sounds unbeatable, right up until the
layers share a weakness. Security
researchers found that a command with
more than 50 subcommands falls back to a
single generic approval prompt, quietly
skipping the per sub command denied
checks, because parsing them all was
freezing the interface. Defense in depth
assumes the layers fail independently.
Here, performance pressure made several
of them degrade at exactly the same
time. Extensibility carries its own
bill. Every hook, plugin, and external
server you add is also new attack
surface. And some real vulnerabilities
lived in the window before the trust
dialogue even appeared. And all that
clever compaction is largely invisible.
When your history gets summarized or
collapsed, you usually can't see what
was dropped. Every one of these is the
direct cost of a strength. Layering,
extensibility, and compression each buy
you something genuine, and each hands
you a brand new failure mode as the

And then the question the paper saves
for last, the one that isn't really
about architecture at all. All of this
amplifies what you can do today, but
does it quietly erode what you
understand over time? The authors are
careful here. They call this a
cross-cutting concern, not a design
value, precisely because the
architecture doesn't actually optimize
for it. But the evidence they gather is
sobering. Anthropic Zone study names a
paradox of supervision. Lean on the AI

protect that second one. It's the rare

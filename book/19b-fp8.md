# 19b. FP8 — the hardware-native quantized float

**Build:** nothing · **Test:** none (kernel math testable with `torch._scaled_mm`)
**Moves:** decode memory traffic (2 bytes → 1), tensor-core rate (FP8 matmuls run 2× FP16 on Ada/Hopper/Blackwell)
**Prereq:** [19. Quantization](19-quantization.md), [02. Arithmetic intensity](02-arithmetic-intensity.md)

---

## The problem

Lecture 19 quantized to **INT8/INT4**: uniform grids with a zero-point. Those
work, but they carry two costs the industry paid real money to avoid:

1. **Zero-point plumbing** — asymmetric ranges need the offset in every
   dequant, and outlier-heavy activations need per-channel or per-group
   scales to stay accurate.
2. **Hardware mismatch** — data arrives as INT8 but the tensor cores on
   modern GPUs have *native FP8 paths* (2× the FP16 rate). Dequantizing to
   FP16 on the way in wastes exactly the speedup you quantized for.

## The idea

FP8 is a **float with 8 bits** — you keep the exponent, you drop the mantissa.
Two encodings exist, and the choice is the whole lecture:

| | E4M3 | E5M2 |
|---|---|---|
| bits | 4 exp / 3 mantissa | 5 exp / 2 mantissa |
| max | 448 | 57344 |
| precision | better | worse |
| used for | **weights + activations** (inference) | **gradients** (training) |

One scale per tensor covers a weight block because the exponent already spans
magnitudes: an E4M3 grid at scale `s` covers values like a mini-float
distribution. That kills the zero-point (symmetric by construction) and the
per-channel scales (Lecture 19 needed them for INT8 because a uniform grid
cannot represent a heavy-tailed weight matrix in one range).

## The math — same shape as Lecture 19

```
   w_fp16 ≈ scale_w × w_fp8          (no zero-point — the exponent absorbs it)

   output = (A_fp8 × B_fp8) × (scale_A × scale_B)
```

The matmul runs entirely in FP8 tensor cores with an FP32 accumulator; the
scale product is one multiply per output block, applied after. Encode side:

```
   scale = max_abs(block) / 448          (E4M3 saturation)
   w_fp8 = clamp(round(w_fp16 / scale))  → overflow saturates, not wraps
```

## Calibration (the accuracy lever)

Pointers, not prose — each is a knob you turn while watching your eval
(Lecture 19's `quality_eval.py`):

- **Scale basis:** per-tensor (cheap, one number) vs per-channel (weight rows
  have different scales; ~free in decode) vs per-block (small groups, like
  GGUF's block scales — see [19c](19c-gguf.md)).
- **Scale selection:** `max_abs` is safe and wastes bits on one outlier;
  percentile (99.9%) trades a clipped outlier for precision on the mass of
  the distribution. Clip → outliers land on ±448, propagate error.
- **Static vs dynamic:** weights = static, calibrate offline once (it's
  Lecture 19's trick, same story). Activations vary per token → per-token
  scale computed at runtime, or accept static scales from calibration data.
- **What to keep in FP16:** the first/last layer and any layer where your
  eval moves (Lecture 19's "keep linear attention in full precision" — same
  rule, same reason: measure, don't assume).

## Hardware reality (why this lecture exists)

| GPU | FP8 tensor cores | FP4 |
|-----|-----------------|-----|
| 3090 (Ampere) | **no** | no |
| A100 (Ampere) | no (TF32 path only) | no |
| Ada (4090) / Hopper (H100) | yes, 2× FP16 | no |
| Blackwell (B200) | yes, 2× FP16 | 2× FP8 |
| B300 | yes | 3× FP8 (per Nvidia specs) |

So FP8 is the *first* quantization in this book that is not purely about
memory: it also changes the **arithmetic rate** of the tensor cores. That's
why the reported numbers are "2×" not "~1.6×" (Lecture 19's INT8 speedup
after dequant overhead).

## Where the pieces live

- **PyTorch:** `torch._scaled_mm` (fp8 matmul with scales), `torch.float8_e4m3fn`
  dtype; `torch.compile` handles FP8 eagerly in Inductor.
- **Triton:** `tl.float8e4nv` / `tl.float8e5` — usable inside the kernels you
  wrote in Lectures 16–18.
- **vLLM:** FP8 W8A8 and W8A16 paths (cutlass + marlin kernels), per-channel
  weight scales, activation scales on the fly. Your I1 "peek" habit applies:
  grep the installed source for `fp8` before trusting docs.
- **Field number (vendor-reported, not measured here):** Adobe's Firefly
  team reported 35% latency reduction via FP8 quantization on A100/H100 —
  treat as ecosystem signal, verify on your own bench.
